# 🚀 迈拓团队 MCU 资料库：高效管理与协作指南（零基础友好版）

## 第一部分：新手破冰（必读，降低学习成本）

对于没用过 Git 的成员，不要一开始就扔给他们命令行。请先用“大白话”向他们解释以下概念，并统一使用图形化工具。

### 1. 大白话解释 Git 概念
*   **仓库 (Repository)** = 团队的“公共资料柜”。
*   **克隆 (Clone)** = 把资料柜里的东西**完整复制**一份到你自己的电脑上。
*   **分支 (Branch)** = 资料的“草稿本”。你在草稿本上怎么乱画，都不会影响资料柜里的“正本”（main 分支）。
*   **提交 (Commit)** = 你的草稿写好后，在本地电脑上**存个档**（此时还没传给团队）。
*   **推送 (Push)** = 把你本地存的档，**上传**到团队的公共资料柜。
*   **拉取 (Pull)** = 把资料柜里别人上传的新东西，**下载**到你自己的电脑上。
*   **PR (Pull Request)** = 向管理员举手申请：“我的草稿写好了，请审核一下，没问题就放进正本吧！”

### 2. 工具推荐（强烈建议新手使用图形界面）
*   **首选：GitHub Desktop**
    *   **理由**：官方出品，全图形化界面，点点鼠标就能完成克隆、提交、推送、解决冲突，**极大降低新手恐惧感**。
    *   **动作**：全员下载安装 GitHub Desktop，并用自己的 GitHub 账号登录。
*   **备选：VS Code 内置 Git**
    *   **理由**：写代码本来就用 VS Code，左侧的“源代码管理”面板可以直接点按钮提交，不用切窗口。

## 第二部分：成员实操手册（日常如何拉取与提交）

请把这一节直接发给团队的新成员，作为他们的“每日操作 SOP”。

### 场景一：第一次把资料库拿到手（克隆）
1. 在浏览器打开团队 GitHub 仓库主页，点击绿色的 **Code** 按钮，选择 **Open with GitHub Desktop**。
2. 在弹出的软件中，选择保存在电脑的哪个文件夹（建议不要放在中文路径或桌面），点击 **Clone**。
3. 等待进度条走完，你的电脑上就有了一份完整的资料库。

### 场景二：每天开始工作前，同步最新资料（拉取 Pull）
> ⚠️ **铁律**：每天打开电脑准备加资料/写代码前，**第一件事永远是拉取最新代码**，防止你改的东西和别人改的东西起冲突！
*   **操作**：打开 GitHub Desktop -> 确保左上角选的是你的分支（如 `develop`） -> 点击顶部的 **Fetch origin** -> 如果出现 **Pull** 按钮，点击它。

### 场景三：整理好一份资料后，上传给团队（提交与推送）
1. **保存文件**：在电脑本地把文档写完，或者把代码编译通过。
2. **查看改动**：打开 GitHub Desktop，左侧会列出你修改或新增的所有文件。
3. **填写存档说明 (Commit)**：在左下角的 `Summary` 框里，用一句话写明你干了什么（例如：`新增 STM32F103 串口通信学习笔记`）。
4. **本地存档**：点击蓝色的 **Commit to develop** 按钮。
5. **上传团队 (Push)**：点击顶部的 **Push origin** 按钮。此时你的资料正式进入团队仓库了！

### 场景四：如何申请合并到正本？（发起 PR）
*如果团队规定大家只能改 `develop`，不能直接改 `main`：*
1. 在 GitHub Desktop 推送成功后，点击顶部的 **Branch** 菜单 -> **Create Pull Request**。
2. 浏览器会自动打开，在网页上点击绿色的 **Create pull request**。
3. 等待管理员审核。

## 第三部分：合并者（管理员/Reviewer）规范与职责

管理员不仅仅是“点通过”的人，更是资料库质量的“守门员”。当成员发起 Pull Request (PR) 时，合并者需要执行以下规范：

### 1. 合并前的“四必查” Checklist
在点击绿色的 "Merge" 按钮前，必须检查该 PR 的内容：
- [ ] **目录规范**：文件是否放进了正确的文件夹？（例如：不能把 51 单片机的代码扔到 STM32 的目录下）。
- [ ] **命名规范**：严禁出现 `新建文本文档.txt`、`未命名1.c`、`test1.c` 这类名字。文件名必须见名知意（如 `LED_Blink_Main.c`）。
- [ ] **垃圾文件清理**：是否不小心上传了编译产生的垃圾文件？（如 Keil 的 `*.bak`, `*.dep`, `Objects/` 目录下的文件）。
- [ ] **大文件拦截**：**Git 不是网盘！** 严禁直接上传大于 `50MB` 的文件（如 MP4 教程视频、大型 PDF 数据手册、几百兆的固件包）。
    *   *解决办法*：大文件请上传到阿里云盘/百度网盘，在 Markdown 文档中贴入**网盘链接和提取码**；或者使用 Git LFS 技术（需管理员配置）。

### 2. 冲突处理原则
当多个成员同时修改了 `README.md` 或同一个文件时，会产生“冲突 (Conflict)”。
*   **新手遇到冲突**：告诉新手**不要慌，不要瞎删代码**。让他们在 GitHub Desktop 中打开 VS Code，根据提示保留需要的代码，或者管理员远程协助解决。
*   **合并者的责任**：如果是复杂冲突，管理员应接手解决，解决后再次测试编译，确保资料没有丢失。

### 3. 分支保护策略设置
进入 GitHub 网页端 -> **Settings** -> **Branches** -> **Add branch protection rule**：
*   **Branch name pattern**: `main`
*   勾选 **Require a pull request before merging** (必须通过 PR 才能合并，不能直接强推)。
*   勾选 **Require approvals**: `1` (至少需要 1 个管理员审核通过)。
*   勾选 **Do not allow bypassing the above settings** (禁止任何人绕过规则，包括管理员自己，防止手滑)。

## 第四部分：提交信息（Commit）规范

为了让以后的“更新日志”清晰可查，请全员遵守以下命名格式：

**格式**：`<类型>(<模块>): <简短描述>`

**MCU 团队常用类型**：
*   `docs`: 纯文档、笔记、学习路线更新（例：`docs(STM32): 补充 DMA 学习笔记`）
*   `feat`: 新增功能、新驱动代码（例：`feat(51): 新增 LCD1602 液晶驱动代码`）
*   `fix`: 修正代码 Bug、修正文档错别字（例：`fix(通用): 修正 I2C 延时函数导致卡死的问题`）
*   `refactor`: 重构代码、调整目录结构（例：`refactor: 将散落的头文件统一移入 include 目录`）
*   `chore`: 更新 `.gitignore`、修改 Readme 等杂项。

### 💡 给团队负责人的落地建议：
1. **开一次“扫盲会”**：花 40 分钟，用投影仪演示一遍“如何用 GitHub Desktop 克隆、修改、提交”，让所有人跟着做一遍。这比发任何文档都管用。

3. **建立正向反馈**：在团队的周会上，口头表扬那些提交了高质量笔记或优化了通用驱动的成员，将“知识分享”纳入团队考核或奖励机制。
